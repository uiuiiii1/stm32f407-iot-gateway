### 三、各器件详细用途说明

#### M1 STM32F407VGT6 核心板
- **定位**：整个系统的大脑，运行FreeRTOS实时操作系统
- **关键资源**：1MB Flash（存Bootloader+应用+OTA备份）、192KB SRAM（任务栈+缓冲区）、3路SPI、3路UART、2路I2C、1路CAN、1路FSMC
- **板载资源**：Type-C供电口、复位按键、BOOT选择按键、LCD接口座、引出全部IO引脚
- **注意**：BOOT0接GND为正常Flash启动，BOOT0接3.3V为ISP串口下载模式

#### M2 1.54寸 TFT 显示屏
- **定位**：本地人机界面，替代原计划的0.96寸OLED
- **典型参数**：240×240分辨率，ST7789或ST7735驱动IC，SPI接口，65K色（RGB565）
- **显示内容规划**：
  - 第1行：系统标题 + 运行状态（在线/离线/采集中）
  - 第2行：IP地址
  - 第3行：温度值 + 单位
  - 第4行：湿度值 + 单位
  - 第5行：RTC时间
  - 第6行：网络状态 + 缓存数据条数
- **接口引脚**：BL（背光）、CS（片选）、DC（数据/命令选择）、SDA（MOSI）、SCL（SCK）、RST（复位）、GND、VCC（3.3V）

#### M3 W5500 以太网模块
- **定位**：硬件TCP/IP协议栈，减轻MCU负担，实现联网上云
- **关键特性**：全硬件TCP/IP（TCP/UDP/ICMP/IPv4/ARP），8个独立Socket，SPI接口，3.3V供电
- **用途**：通过MQTT或HTTP协议将采集的温湿度数据上传到云端服务器（如阿里云IoT、腾讯云IoT、或自建MQTT broker）
- **注意**：W5500芯片是3.3V器件（常见模块板载LDO可接受5V输入，按实物确认，严禁把5V直接接到芯片侧引脚）；SPI速率策略：初始化先降到3MHz以下，读到版本寄存器VERSIONR（0x0019）=0x04确认SPI链路正常后再逐步提速；**面包板+杜邦线走线下14MHz左右是实际稳定上限，80MHz只适合PCB短走线，本项目按14MHz封顶**

#### M4 SP3485 RS485收发模块
- **定位**：TTL电平 ↔ RS485差分信号的转换桥梁
- **关键引脚**：VCC（3.3V）、GND、TX（接MCU RX）、RX（接MCU TX）、DE/RE（收发方向控制，接MCU GPIO）
- **工作模式**：
  - DE=1, RE=1 → 发送模式（MCU向总线发数据）
  - DE=0, RE=0 → 接收模式（MCU从总线收数据）
- **注意**：必须买3.3V版本，5V的MAX485与F407电平不匹配

#### M5 温湿度变送器（RS485 Modbus RTU从站）
- **定位**：真实工业传感器，提供温湿度数据源
- **通信协议**：Modbus RTU，作为从站响应主站（网关）的读寄存器指令
- **典型寄存器**（需向商家确认具体地址表）：
  - 温度寄存器：通常地址0x0000，值=实际温度×10（如25.5℃→0x00FF=255）
  - 湿度寄存器：通常地址0x0001，值=实际湿度×10
- **供电**：5~28V宽压，项目中接5V
- **默认参数**：波特率9600，数据位8，停止位1，无校验，从站地址0x01（需向商家确认）

#### M6 DS1307 RTC时钟模块
- **定位**：实时时钟，为采集数据提供精确时间戳
- **关键特性**：I2C接口，7位地址0x68（8位写0xD0/读0xD1），带CR2032电池掉电走时，BCD码计时
- **用途**：每条温湿度数据附带年月日时分秒，断网缓存时按时间排序，联网补传时按时间顺序发送
- **⚠️ 供电修正（v1.1）**：**模块VCC必须接5V，不能接3.3V**。DS1307手册规定VCC=4.5~5.5V，且VCC低于约1.25×VBAT（CR2032为3V，即约3.75V）时芯片进入电池备份模式、I2C完全无响应。F407的PB6/PB7是FT（5V tolerant）引脚，模块上拉到5V的I2C总线可直接连接，无需电平转换。
- **注意**：DS1307精度一般（月误差±几分钟），项目够用；I2C上拉电阻模块通常已自带。若模块5V供电仍工作异常，换DS3231模块（3.3V/5V通用、温补晶振年误差约1分钟、寄存器与DS1307高度相似，见补购清单B3）

#### M7 W25Q64 外部Flash
- **定位**：8MB串行Flash，用于数据持久化存储
- **分区规划**（v1.1与阶段10双槽方案对齐）：
  - 扇区0（4KB）：配置参数区（云端地址、设备ID、波特率等）
  - 扇区1~255（约1MB）：断网数据缓存区（循环写入，磨损均衡）
  - 扇区256~383（512KB）：OTA新固件下载区
  - 扇区384~511（512KB）：OTA旧固件备份区（升级前备份当前应用，用于回滚）
  - 扇区512~2047（约6MB）：预留扩展（可借给数据缓存区扩容）
- **关键特性**：SPI接口，24位地址，扇区擦除（4KB），页编程（256字节），JEDEC ID 0xEF4017
- **注意**：W25Q64是3.3V器件

#### M8 CH340 USB转TTL
- **定位**：电脑与主控之间的串口通信桥梁
- **用途**：
  - 程序下载（配合FlyMcu或Keil的ISP下载）
  - 串口调试打印（printf输出运行日志、变量值、错误信息）
- **接线**：CH340 TXD → 主控 UART1 RX（PA10），CH340 RXD → 主控 UART1 TX（PA9），GND共地
- **注意**：TX/RX要交叉连接；CH340的3.3V/5V输出不要给整个系统供电，仅做信号

#### M14 TJA1050 CAN收发器
- **定位**：CAN控制器（F407片上bxCAN）↔ CAN差分总线的物理层转换
- **关键引脚**：VCC（5V）、GND、TXD（接MCU CAN_TX）、RXD（接MCU CAN_RX）、CANH、CANL
- **用途**：可选扩展，采集CAN总线设备数据（如汽车OBD、工业PLC），车企/工控方向简历加分
- **注意**：TJA1050是5V供电；其TXD输入为TTL电平（数据手册VIH≥2.0V），F407的3.3V推挽输出可直接驱动；RXD输出高电平接近5V，接PA11——F407的FT（5V tolerant）引脚，可直接连接，无需电平转换；总线两端各接120Ω终端电阻

#### M16 SD卡模块（5V版）
- **定位**：大容量本地存储，用于"数据黑匣子"功能
- **关键特性**：5V供电（板载电平转换芯片），SPI接口，支持SDHC卡（≤32GB）
- **用途**：存储历史采集数据，可按天/按文件存储，支持FatFS文件系统
- **注意**：本项目用5V版模块（板载LDO+电平转换），按5V接线最稳妥；SD/SDHC卡本身一律是3.3V信号，"≤2GB的SD卡与2~32GB的SDHC"只是卡容量规格差异、与模块供电无关（v1.1修正）；SD卡必须格式化为FAT32（FatFS默认不支持exFAT，除非开启FF_FS_EXFAT）

#### M18 Air780E 4G模块
- **定位**：以太网不可用时的备用上云通道，双链路冗余
- **关键特性**：Cat.1 bis，UART AT指令控制，支持MQTT/TCP/HTTP，需要物联网SIM卡
- **供电**：射频发射峰值1~2A，不能靠开发板USB供电；建议整机换5V 3A适配器（见补购B5），模块电源引脚就近并联≥470µF电容——供电不足的典型症状是MQTT连上后反复掉线重启
- **用途**：检测到W5500网络断开且持续无法恢复时，自动切换到4G链路上传数据
- **注意**：4G模块是可选高级功能，项目后期再做；需要单独购买物联网SIM卡（移动/电信）

### 五、供电方案

```
5V 2A电源适配器
    ├── 5V → 温湿度变送器 VCC
    ├── 5V → SD卡模块 VCC
    ├── 5V → TJA1050 VCC
    ├── 5V → Air780E VCC（独立供电，峰值1A）
    └── 5V → STM32核心板 Type-C或5V引脚（板载AMS1117转3.3V）
                                          ├── 3.3V → W5500 VCC
                                          ├── 3.3V → SP3485 VCC
                                          ├── 3.3V → W25Q64 VCC
                                          ├── 3.3V → DS1307 VCC
                                          ├── 3.3V → TFT屏 VCC
                                          └── 3.3V → 各模块上拉电阻
```

> **关键**：所有模块GND必须连在一起（共地），否则通信异常。5V 2A电源是必须的，USB供电电流不够。
> **v1.1补充**：W5500的3.3V由核心板同一颗AMS1117提供——单LDO供电天然规避了VDD/VDDA分路LDO上电时序不一致引起的W5500冷启动概率性初始化失败，这个接法不要改成模块独立供电。阶段0~10用2A适配器足够，做阶段13（4G）时换5V 3A（补购B5）。

### 二、Keil工程创建步骤

1. 打开STM32CubeMX，新建项目，选择MCU为STM32F407VGTx
2. 配置系统时钟：HSE（外部晶振，通常8MHz或25MHz，看核心板原理图），PLL倍频至168MHz
3. 按"最终无冲突引脚分配表"配置每个外设的GPIO和复用功能；**SYS → Debug 必须选 Serial Wire**（否则PB3/PB4被JTAG占用，SPI3的TFT屏不工作，也无法用ST-Link在线调试）
4. 配置UART1：115200波特率，8数据位，1停止位，无校验
5. 配置UART2：9600波特率（匹配温湿度变送器默认值），8N1
6. 配置SPI1：主机模式，8位，CPOL=Low, CPHA=1Edge（W5500要求Mode0），预分频器初始设为64（2.625MHz），稳定后改2（42MHz）
7. 配置SPI2：主机模式，8位，Mode0，预分频器初始64
8. 配置SPI3：主机模式，8位，Mode0，预分频器初始64
9. 配置I2C1：标准模式100kHz或快速模式400kHz
10. 配置CAN1：500kbps（常用），工作模式正常
11. 配置GPIO输出：各CS、RST、DC、BL、DIR、LED
12. 生成代码（选择MDK-ARM V5）
13. 在Keil中打开生成的工程，添加FreeRTOS源码
14. 配置工程选项：C/C++ → Define 添加 USE_HAL_DRIVER, STM32F407xx；Optimization选-O1（调试阶段选-O0）
15. Debug → 选择ST-Link或J-Link（如果用调试器），或用FlyMcu串口下载

## 第四部分：分阶段开发计划

### 总体原则
- 从易到难，每一步先验证通过再进入下一步
- 每完成一个模块，保存一个可工作的工程备份
- 先裸机调通每个外设，再移植FreeRTOS整合
- 先核心功能（采集+显示+上传），后高级功能（缓存+OTA+4G+CAN）

---

### 阶段0：硬件验证与点灯（预计0.5天）

**目标**：确认核心板能正常下载程序、运行、串口输出。

**操作步骤**：
1. 核心板插Type-C供电（或5V引脚），确认电源灯亮
2. CH340接UART1（PA9/PA10），插电脑，确认设备管理器出现COM口
3. CubeMX生成最简工程（只配UART1 + GPIO PC13输出 + 系统时钟）
4. 在main.c中添加：LED闪烁（500ms周期）+ printf("System Start\r\n")
5. 编译、下载、运行
6. 串口助手收到"System Start"，LED闪烁 → 验证通过

**验证标准**：
- [ ] 程序能正常下载
- [ ] LED按预期闪烁
- [ ] 串口能收到printf输出
- [ ] 复位后重新运行正常

**常见问题**：
- 串口收不到：检查TX/RX是否交叉、GND是否共地、波特率是否一致
- 程序下载失败：检查BOOT0位置、CH340驱动、串口是否被占用

### 阶段1：1.54寸TFT屏显示（预计1天）

**目标**：屏幕能显示文字、数字、颜色填充。

**操作步骤**：
1. 按接线表连接TFT屏（SPI3：PB3/PB5，CS=PA15，DC=PC7，RST=PC8，BL=PC9）
2. 确认屏的驱动IC：查看商家资料，常见为ST7789（240×240）或ST7735（128×128/128×160）
3. 添加对应驱动文件（lcd.c/lcd.h），实现：
   - `LCD_Init()`：初始化序列（复位→发送初始化命令→开显示）
   - `LCD_Clear(color)`：全屏填充
   - `LCD_DrawPoint(x,y,color)`：画点
   - `LCD_ShowChar(x,y,ch,color,bg,size)`：显示单个ASCII字符
   - `LCD_ShowString(x,y,str,color,bg,size)`：显示字符串
   - `LCD_ShowNum(x,y,num,len,color,bg,size)`：显示数字
4. 字模数据：使用PCtoLCD2002取模软件生成ASCII字模（16×8或24×12），存入font.c
5. main.c中测试：清屏→显示"Gateway Test"→显示数字12345→显示IP"192.168.1.100"
6. 编译下载，观察屏幕

**验证标准**：
- [ ] 屏幕背光点亮
- [ ] 全屏填充颜色正常（无花屏、无偏移）
- [ ] 英文字符显示清晰、位置正确
- [ ] 数字显示正确
- [ ] 多次刷新不出现残影或错位

**常见问题**：
- 屏幕不亮：检查BL引脚是否拉高、VCC是否3.3V
- 花屏/白屏：SPI速率太高（降低预分频器）、RST时序不对、初始化命令不对
- 颜色反转/偏移：确认驱动IC型号（ST7789 vs ST7735），不同IC的初始化命令和扫描方向不同
- 字符乱码：字模取模方式与显示函数不匹配（逐行式/逐列式、正序/倒序）

### 阶段2：DS1307 RTC时间读取（预计0.5天）

**目标**：能读取并设置当前时间，串口打印正确时间。

**操作步骤**：
1. 连接DS1307（I2C1：PB6/PB7，**模块VCC接5V**），插入CR2032电池
2. CubeMX配置I2C1：100kHz标准模式
3. 实现ds1307.c/ds1307.h：
   - `DS1307_Init()`：检查器件是否响应（读地址0x00）
   - `DS1307_SetTime(y,m,d,h,min,s)`：设置时间（BCD码转换）
   - `DS1307_GetTime(&time)`：读取时间
   - BCD↔十进制转换函数
4. main.c中：设置一个时间→循环读取→串口打印"2026-09-29 12:00:00"
5. 断电10秒再上电，确认时间继续走（电池备份生效）

**验证标准**：
- [ ] I2C能扫描到DS1307地址（0x68）
- [ ] 设置时间后读取值一致
- [ ] 时间每秒递增正确
- [ ] 掉电后时间不丢失（电池供电）

**常见问题**：
- I2C扫描不到设备：检查SDA/SCL是否接反、上拉电阻是否存在、模块VCC是否接的5V（接3.3V时DS1307进入电池模式、I2C无响应，这是本模块最常见故障）
- 时间不走：检查CH位（寄存器0x00的bit7）是否为0（0=振荡器开启）
- 时间值异常：BCD码没有正确转换（DS1307寄存器存的是BCD码，不是二进制）

### 阶段3：RS485 Modbus采集温湿度（预计1.5天）

**目标**：通过RS485读取温湿度变送器数据，解析出温度和湿度值。

**操作步骤**：

#### 3.1 先用USB转RS485在电脑端验证变送器（必做！）
1. USB转RS485插入电脑，安装CH340驱动
2. USB转RS485的A/B接温湿度变送器的A/B，变送器接5V电源
3. 打开Modbus Poll或串口调试助手
4. 发送读保持寄存器指令（需根据商家提供的寄存器表）：
   - 典型指令：`01 03 00 00 00 02 C4 0B`
     - 01=从站地址，03=功能码（读保持寄存器），0000=起始地址，0002=寄存器数量，C40B=CRC16
   - 预期回复：`01 03 04 00 FF 01 02 XX XX`（温度25.5℃，湿度25.8%为例）
5. 确认变送器能正常回复数据，记录：从站地址、波特率、温度寄存器地址、湿度寄存器地址、数据换算公式

#### 3.2 STM32端实现Modbus RTU主站
1. 连接SP3485（UART2：PA2/PA3，DIR=PA4）
2. CubeMX配置UART2：9600波特率（或变送器实际波特率），8N1
3. 实现modbus.c/modbus.h：
   - `MODBUS_SendRead(slave_addr, reg_addr, reg_num)`：组装读寄存器指令+CRC16，DE拉高→发送；**等UART的TC（Transmission Complete）标志置位后再拉低DE切回接收**——盲等固定延时容易截断最后1~2字节，是RS485最经典的偶发丢包原因
   - `MODBUS_Receive(buf, timeout)`：等待从站回复，超时返回错误
   - `CRC16(data, len)`：Modbus CRC16校验算法（多项式0xA001）
   - `MODBUS_ReadTempHum(&temp, &hum)`：完整流程：发指令→收回复→CRC校验→解析数据→换算实际值
4. 数据解析：
   - 温度值 = 寄存器值 / 10.0（如果是放大10倍存储）
   - 湿度值 = 寄存器值 / 10.0
5. main.c中：每2秒读一次温湿度，串口打印"Temp: 25.5C, Hum: 60.2%"

**验证标准**：
- [ ] USB转RS485电脑端能读到变送器数据（确认变送器本身正常）
- [ ] STM32能发出正确的Modbus指令（可用USB转RS485在电脑端监听）
- [ ] STM32能收到变送器回复
- [ ] CRC校验通过
- [ ] 解析出的温湿度值合理（与电脑端读到的一致）
- [ ] 连续读取10次无丢包、无异常值

**常见问题**：
- 收不到回复：DE/RE方向控制时序不对（发完指令要延迟一小段再切回接收）、A/B线接反、波特率不匹配
- CRC校验失败：字节丢失（波特率误差大）、接收缓冲区溢出、从站地址错误
- 数据异常：寄存器地址不对、数据大小端搞反、换算公式不对（必须以商家提供的寄存器表为准）
- 偶尔丢包：RS485总线没有终端电阻（长距离时）、发送间隔太短（至少间隔100ms）

### 阶段4：W25Q64 Flash读写（预计1天）

**目标**：能对W25Q64进行读ID、擦除、写数据、读数据操作。

**操作步骤**：
1. 连接W25Q64（SPI2：PB13/PB14/PB15，CS=PB12）
2. 实现w25q64.c/w25q64.h：
   - `W25Q64_ReadID()`：发送0x9F命令，读取JEDEC ID（应为0xEF4017）
   - `W25Q64_WriteEnable()`：发送0x06命令
   - `W25Q64_WaitBusy()`：读状态寄存器1（0x05），等待BUSY位清零
   - `W25Q64_SectorErase(addr)`：扇区擦除（0x20命令，4KB对齐）
   - `W25Q64_PageProgram(addr, data, len)`：页编程（0x02命令，≤256字节）
   - `W25Q64_ReadData(addr, buf, len)`：读数据（0x03命令）
3. main.c中测试：
   - 读ID，确认是0xEF4017
   - 擦除扇区0
   - 写入测试数据"Hello W25Q64"
   - 读回数据，串口打印对比
4. 实现简单的存储管理：
   - 定义数据结构体：`{uint32_t timestamp; float temp; float hum; uint8_t status;}` 约13字节
   - `Flash_SaveData(data)`：追加写入缓存区
   - `Flash_ReadData(index, &data)`：读取指定位置数据
   - `Flash_GetDataCount()`：获取缓存数据条数

**验证标准**：
- [ ] JEDEC ID读取正确（0xEF4017）
- [ ] 擦除后读取全0xFF
- [ ] 写入后读回数据一致
- [ ] 跨页写入正常（写入>256字节时自动分页）
- [ ] 掉电后数据不丢失
- [ ] 连续写入100条数据后读取全部正确

**常见问题**：
- ID读不到：SPI模式不对（W25Q64用Mode0）、CS时序不对、SPI速率太高
- 写入失败：没有先发Write Enable命令、没有等待Busy结束、地址没有页对齐
- 数据不对：地址计算错误、大小端问题

### 阶段5：W5500以太网联网（预计2天）

### 阶段8：移植FreeRTOS多任务（预计3~4天）

**目标**：将所有功能整合到FreeRTOS中，多任务并行运行。

**操作步骤**：
1. 移植FreeRTOS V10.x到Keil工程：
   - 添加源码：tasks.c、queue.c、list.c、timers.c、event_groups.c、heap_4.c、port.c
   - **把HAL时基移出SysTick**（CubeMX：SYS → Timebase Source 选TIM6/TIM7）：FreeRTOS要独占SysTick作节拍源，两者共用会出现HAL_GetTick不走、任务里HAL_Delay假死等诡异现象
   - 配置FreeRTOSConfig.h：
     - configCPU_CLOCK_HZ = 168000000
     - configTICK_RATE_HZ = 1000
     - configTOTAL_HEAP_SIZE = 60*1024（60KB，F407有192KB SRAM够用）
     - configMAX_PRIORITIES = 10
     - 使能configUSE_MUTEXES、configUSE_COUNTING_SEMAPHORES
2. 任务划分：

| 任务名 | 优先级 | 栈大小 | 功能 | 周期 |
|---|---|---|---|---|
| CollectTask | 5（高） | 512字 | RS485采集温湿度，数据放入队列 | 2秒 |
| NetworkTask | 4 | 1024字 | W5500 MQTT连接+发布数据 | 5秒 |
| DisplayTask | 3 | 512字 | TFT屏刷新显示 | 1秒 |
| StorageTask | 3 | 512字 | 断网时写Flash缓存，联网时补传 | 事件触发 |
| WatchdogTask | 6（最高） | 256字 | 喂独立看门狗，监控各任务心跳 | 1秒 |

> 栈大小单位是**字（word）**，Cortex-M上1字=4字节（512字=2KB、1024字=4KB）。上表为初始值，用uxTaskGetStackHighWaterMark()实测后回调。

3. 任务间通信（v1.1修正）：
   - 采集数据队列：`xQueueData`（CollectTask发，**NetworkTask作为唯一消费者**——FreeRTOS队列是出队模型，两个任务收同一个队列时每条数据只会被其中一个拿到，DisplayTask不能也从这里收）
   - 最新值共享变量：`xLatestData`（含temp/hum/timestamp，由`xDataMutex`保护；CollectTask写入、DisplayTask读取显示，与队列互不干扰）
   - 网络状态信号量/事件组：`xEventGroupNet`（bit0=网络在线，bit1=MQTT已连接）
   - 互斥锁：`xSPIMutex`（保护**SPI2**总线——W25Q64和SD卡分时复用；SPI1上只有W5500一个设备，不需要互斥）
4. 每个任务实现：
   - 任务初始化（外设初始化只做一次）
   - 任务主循环（vTaskDelayUntil精确周期）
   - 错误处理（通信失败重试、超时降级）
   - **任务内延时一律用vTaskDelay/vTaskDelayUntil、禁止HAL_Delay；需要关中断的临界区用taskENTER_CRITICAL()/taskEXIT_CRITICAL()——直接__disable_irq()会停掉SysTick，整个系统假死**
5. 看门狗：IWDG独立看门狗，超时2秒，WatchdogTask定期喂狗；每个任务设置心跳标志，WatchdogTask检查所有任务心跳，任一任务卡死超过5秒则不喂狗→系统复位

**验证标准**：
- [ ] FreeRTOS调度正常，所有任务都在运行
- [ ] 任务间数据传递正确（队列无丢失）
- [ ] SPI总线共享无冲突（互斥锁生效）
- [ ] 看门狗正常喂狗，不会意外复位
- [ ] 系统连续运行24小时无死机、无内存泄漏
- [ ] 用Keil查看任务栈使用情况，无栈溢出

**常见问题**：
- 任务栈溢出：增大栈大小，用uxTaskGetStackHighWaterMark()检查
- 系统卡死：优先级反转（用互斥锁）、死锁（检查锁的获取顺序）、中断优先级配置错误
- 整合后系统假死/HAL_GetTick不走：HAL时基与FreeRTOS共用SysTick（把时基移到TIM6/TIM7）；代码里直接__disable_irq()同样造成此现象
- W5500整合进RTOS后初始化失败/连不上：复位后延时≥50ms再访问；任务内等待一律osDelay/vTaskDelay；裸机阶段调通的SPI速率在加互斥锁后如不稳，先降回3MHz复测再提速
- 内存不足：减小configTOTAL_HEAP_SIZE或优化任务栈
- 中断不工作：FreeRTOS的中断优先级分组配置（NVIC_PRIORITYGROUP_4），优先级数值大于configMAX_SYSCALL_INTERRUPT_PRIORITY的中断才能调用FreeRTOS API

### 阶段9：断网缓存+联网补传（预计1.5天）

**目标**：网络断开时数据存入W25Q64，网络恢复后按时间顺序补传。

**操作步骤**：
1. 网络状态检测：
   - NetworkTask定期检查W5500 PHY状态和MQTT连接状态
   - 连续3次发布失败→判定为断网→设置事件标志位
2. 断网缓存逻辑（StorageTask）：
   - 检测到断网→将采集数据追加写入W25Q64缓存区
   - 缓存区采用循环写入（写满后从头部覆盖最旧数据）
   - **写指针/条数不要每次落盘到配置区**（v1.1修正）：4KB配置扇区擦写寿命约10万次，每2秒更新一次指针几天就磨穿。正确做法是上电扫描缓存区、按flag/CRC重建写指针与条数——NOR Flash擦后全0xFF、按字节编程的特性天然支持"追加+最后写标志"的日志式写入
3. 联网补传逻辑：
   - 检测到网络恢复→先补传缓存数据，再发实时数据
   - 补传按时间顺序从旧到新
   - 每条补传成功后更新读指针
   - 补传期间实时数据继续缓存（避免丢失）
4. 数据结构：
   ```c
   typedef struct {
       uint32_t timestamp;  // RTC时间戳（Unix时间）
       float temp;
       float hum;
       uint8_t flag;        // 提交标志：整条记录写完后最后才改写为0=有效（掉电写到一半的记录flag仍是0xFF，天然失效）
       uint8_t crc;         // 前12字节的CRC8：读出时校验，拦截半条记录/位翻转的脏数据
   } DataRecord_t;  // 14字节，按4字节对齐占16字节
   ```
5. 磨损均衡：缓存区固定为Flash的特定扇区范围，循环使用
6. 容量与寿命核算（v1.1新增，面试高频考点）：
   - 容量：缓存区1MB ÷ 16字节/条 ≈ 6.5万条；2秒采样≈4.3万条/天，**满缓存仅支撑断网约1.5天**。需要更长容忍度：从预留区再借2MB给缓存（≈4.5天），或断网时自动降为10秒/条（≈7天）
   - 磨损：循环写满一轮≈1.5天，每个4KB扇区约1.5天擦除一次，按10万次寿命算可用≈400年，循环写入方案本身磨损无忧
   - 掉电安全：NOR Flash先擦后写、擦除中掉电该扇区数据全丢——靠"flag最后写+CRC校验"把损坏范围限制在正在写的1条内，重启扫描剔除即可

**验证标准**：
- [ ] 拔网线后数据正常写入Flash（不丢失）
- [ ] 插网线后缓存数据按时间顺序补传
- [ ] 补传完成后实时数据恢复正常发送
- [ ] 缓存区写满后循环覆盖（不越界）
- [ ] 掉电后缓存数据不丢失，上电继续补传
- [ ] 补传期间新采集的数据不丢失
- [ ] 写入中途断电/复位，重启后扫描重建正确：除正在写的一条外其余数据完好，补传顺序正确

### 阶段10：OTA远程升级（预计4~5天）

**目标**：通过网络下载新固件到W25Q64，校验后切换运行，支持回滚。

**操作步骤**：

#### 10.1 Flash分区规划
```
0x08000000 ──────────────
           │ Bootloader  │  32KB（0x08000000~0x08007FFF）
0x08008000 ──────────────
           │ 应用程序A   │  480KB（0x08008000~0x0807FFFF）
0x08080000 ──────────────
           │ 预留512KB   │  0x08080000~0x080FFFFF（可作第二应用槽/参数区）
0x080FFFFF ──────────────  ← F407VGT6 Flash结束（共1MB；v1.1修正：原文止于0x08080000，少算一半）
           
W25Q64外部Flash：
0x00000000 ──────────────
           │ 配置参数区  │  4KB
0x00001000 ──────────────
           │ 数据缓存区  │  约1MB
0x00100000 ──────────────
           │ 新固件下载区 │  512KB（0x00100000~0x0017FFFF）
0x00180000 ──────────────
           │ 旧固件备份区 │  512KB（0x00180000~0x001FFFFF，升级前备份当前应用）
0x00200000 ──────────────
           │ 预留扩展区   │  约6MB（可借给数据缓存区扩容）
0x00800000 ──────────────
```

#### 10.2 Bootloader开发
- 独立工程，运行在0x08000000
- 功能：
  - 检查W25Q64中是否有新固件（标志位+固件大小+CRC）
  - 有新固件→校验CRC→**先把当前应用备份到W25Q64旧固件区**→写入内部Flash应用区→清除标志→跳转应用
  - 无新固件→直接跳转应用（0x08008000）
  - 跳转函数：设置MSP→设置PC→禁用中断
- 应用程序中断向量表偏移：SCB->VTOR = 0x08008000
- **Keil工程同步修改**：Options → Target → IROM1起始地址0x08008000、Size 0x78000（480KB）——不改的话代码仍链接到0x08000000，Bootloader跳转后必然跑飞

#### 10.3 应用程序OTA功能
- MQTT订阅OTA主题："gateway/ota/gw001"
- 收到OTA指令（包含固件URL/大小/CRC）→进入OTA模式
- 通过HTTP或MQTT分片下载固件到W25Q64的新固件下载区
- 下载完成→校验CRC→写入升级标志→复位
- 复位后Bootloader自动完成固件更新

#### 10.4 回滚机制（v1.1重写：必须双槽才能真正回滚）
> 原方案只存一份新固件——新固件写入内部Flash后旧版本即被覆盖，"回滚"无从谈起。升级流程改为两步备份：
1. 下载新固件到W25Q64"新固件下载区"并校验CRC
2. **先把内部Flash当前应用整体备份到"旧固件备份区"**（备份自带CRC），再擦写内部Flash应用区
3. 新固件首次运行正常（联网成功+连续稳定运行N分钟）才置位"升级成功标志"
4. 新固件看门狗复位≥3次仍未确认 → Bootloader从"旧固件备份区"恢复旧版本；若旧备份区CRC也损坏，停在Bootloader等待串口重烧
> 进阶替代：利用内部Flash预留的0x08080000~0x080FFFFF做A/B双应用槽，Bootloader按标志选择启动槽位，连备份/恢复的整块拷贝都能省掉

**验证标准**：
- [ ] Bootloader能正常跳转到应用
- [ ] 应用能正常下载固件到W25Q64
- [ ] CRC校验正确
- [ ] 升级后新固件正常运行
- [ ] 升级失败（CRC错误）能回滚到旧版本
- [ ] 升级过程中断电不会变砖（Bootloader始终可用）

**注意**：OTA是本项目最复杂的功能，建议放在最后做。如果时间紧张，可以先做Bootloader+本地串口升级，网络OTA作为扩展。

### 一、必备调试手段

| 调试对象 | 工具/方法 | 用途 |

| 代码调试 | ST-Link + Keil Debug | 设断点、单步执行、查看寄存器和变量 |

### 二、通用调试流程

1. **先确认硬件**：用万用表测各模块VCC电压是否正确（3.3V/5V），GND是否共地
2. **再确认通信**：用USB转串口/逻辑分析仪监听数据，确认MCU发出的数据正确
3. **然后确认外设**：单独测试每个外设，确认能正常工作
4. **最后整合**：整合时如果出问题，回退到上一个能工作的版本，逐个模块排查

### 三、常见故障排查表

| 现象 | 可能原因 | 排查方法 |
|---|---|---|
| 程序下载后不运行 | BOOT0位置不对、复位电路、程序跑飞 | 检查BOOT0接GND、按复位键、串口看有无输出 |
| 串口无输出 | TX/RX接反、波特率不对、GND未共地 | 交叉TX/RX、确认波特率、测GND连通 |
| SPI设备无响应 | SPI模式不对、速率太高、CS时序 | 降低SPI速率到1MHz、确认Mode0/Mode3、用逻辑分析仪看CS |
| I2C设备无响应 | SDA/SCL接反、上拉电阻、地址错误 | 换线、加4.7K上拉、用I2C扫描程序找地址 |
| RS485收不到数据 | A/B接反、DE方向控制、波特率 | 交换A/B、检查DE时序、电脑端监听确认变送器有回复 |
| W5500连不上网 | 网线、IP配置、SPI通信 | Ping测试、检查PHY状态、降低SPI速率 |
| MQTT连接失败 | broker地址、网络、ClientID | 电脑端MQTT.fx测试同一broker、检查网络 |
| 系统死机 | 栈溢出、内存越界、优先级反转 | 关中断看是否还死、检查数组边界、uxTaskGetStackHighWaterMark |

## 第七部分：简历项目描述参考

### 一句话描述
基于STM32F407+FreeRTOS的多功能工业物联网网关，通过RS485 Modbus RTU采集温湿度数据，经W5500硬件TCP/IP以太网上传云端，支持断网数据缓存补传、OTA远程升级与失败自动回滚、TFT本地显示，可扩展CAN总线和4G双链路。

### 技术栈
STM32F407 / FreeRTOS / Modbus RTU / W5500 / MQTT / SPI / I2C / RS485 / CAN / OTA / W25Q64

### 核心亮点（面试可深挖）
1. FreeRTOS多任务调度：5个任务（采集/网络/显示/存储/看门狗），队列（单一消费者）+事件组+互斥锁通信
2. Modbus RTU主站：CRC16校验、超时重传、多节点轮询
3. W5500硬件TCP/IP：对比LwIP软件协议栈，SPI驱动+Socket编程
4. 数据可靠性：断网Flash日志式缓存（flag最后写+CRC校验的掉电安全设计）+联网按时间戳排序补传+扇区轮转磨损均衡
5. OTA升级：Bootloader+新/旧固件双槽备份+CRC校验+失败自动回滚
6. 看门狗：独立看门狗+任务心跳监控，死机自动复位

### 客观定位与呈现策略（v1.1新增）
- **定位**："STM32+FreeRTOS+MQTT网关"是嵌入式求职的高频项目原型，单靠功能清单区分度有限；真正拉开差距的是断网缓存的数据可靠性设计、OTA Bootloader回滚，以及面试中能讲清每一个设计取舍
- **不要重点写**：TFT屏驱动、I2C读RTC——一句话带过即可；CAN/4G若只做了基础收发，标注"扩展设计"而非核心成果（面试深挖答不上反而减分）
- **描述采用"问题-方案-数据"三段式**，示例：
  > 断网期间采集数据100%丢失 → 设计W25Q64日志式循环缓存（flag+CRC掉电安全、扇区轮转磨损均衡）+按时间戳排序补传 → 连续离线24h后恢复网络，1200条缓存数据100%按序补传、零丢失零重复
- **FreeRTOS要写出具体工程决策**，示例："5任务（优先级3~6），CollectTask以vTaskDelayUntil固定2s周期采集；队列单一消费者+互斥保护的最新值共享变量供显示任务读取；SPI2多设备互斥锁仲裁；IWDG 2s+各任务心跳位监控；任务栈按uxTaskGetStackHighWaterMark实测调优"
- **加分动作**：GitHub仓库真实提交历史（不要一次性push）、README画系统架构图+Flash分区图、录一段"拔网线→缓存→补传→OTA升级失败自动回滚"的演示视频、备好2~3个真实调试战例（如RS485偶发丢包最终定位到DE切换时序）
